# ADR 0001: A BLAKE3 core in Bend2, and the baseline we race

Date: 2026-10-26
Status: accepted

## Context

The goal is the fastest BLAKE3 we can write in Bend2 (v2.0.39, `~/.bend`),
on this machine: Apple M5 Pro, 18 CPU cores (6 + 12), 20-core GPU, 64 GB
unified memory, Apple clang 21. It should beat the official Rust/C BLAKE3
on its parallel CPU and GPU paths, for big inputs and for many small files.

What we learned from the guides and the emitted C before writing code:

- A *flat* def (no parallel let, bang, closure or non-tail self call)
  compiles to one native C loop (`spin_N`), with U32 values held in `u32`
  locals.
- A record of scalars (`CV{8 x U32}`, `M16{16 x U32}`) is unboxed: it is
  passed as separate registers and returned through a small `o[]` array, all
  `static inline`. So `compress` compiles to straight-line scalar C that
  clang optimises like hand-written code.
- `Array<U32>` is a packed native buffer of u32 (`TAG_BUF`), and `a[i]` is
  one load (`blk_read`). Matching on `ANode` would *copy* half of it, so we
  never match on the input.
- `Array.fork` (`@unsafe`) makes two handles to one array in O(1): a refcount
  bump. That is how the input travels down the fork tree.
- `match` only destructures parameters, never computed values. Results of
  `a[i]` are `(array, word)` pairs, so a 16-word block load is a chain of 16
  one-read defs. clang inlines the chain back into 16 loads.

## Decision

- `bend/blake3.bend` is generated by `bend/tools/gen_blake3.py`. The
  generator only unrolls what Bend's syntax forces us to (a round's 64
  scalar lets, the 16-step loader). The tree, chunk loop and hex output are
  hand-written templates inside it.
- One round is one def: the four column and four diagonal G steps inline.
  The message permutation is a record re-ordering (`perm`), which is free
  in registers. `compress` applies seven rounds.
- The tree follows BLAKE3's left-full shape with a `Nat` depth `k` that
  shrinks by one per level (so the termination checker accepts it), and a
  `Bool` saying whether this level has a parent node. A node's two subtrees
  are one parallel let: `l r = tree(...) tree(...)`.
- Each tree node carries a *pair* of array handles, so it can destructure
  the pair as a parameter and fork each half again for its children. This
  avoids mutual recursion, which Bend forbids.
- The input length is a U32, so v1 inputs are under 4 GiB.

## Correctness

`bend/test/vectors.bend` rebuilds the official inputs (byte i = i % 251) and
`test/check.py` compares with `test_vectors/test_vectors.json`:
35/35 lengths match (0 through 102400 bytes, every chunk/block boundary).

## Baseline numbers (64 MiB in memory, warm, same data, same digest)

| implementation                          | time    | GB/s |
|-----------------------------------------|---------|------|
| Rust `blake3` 1.8.7, NEON + rayon       | 2.4 ms  | ~28  |
| Rust `blake3`, NEON, 1 thread           | 28 ms   | 2.4  |
| **Bend v1, CPU pool (18 threads)**      | 6.6 ms  | 10.2 |
| **Bend v1, 1 thread**                   | 59.5 ms | 1.13 |
| **Bend v1, GPU (`hash!`)**              | 3.2 ms  | 21   |

`b3sum` end to end (mmap + rayon, file in page cache): 1 GiB in 45.8 ms,
64 MiB in 5.6 ms, 10,000 x 4 KiB files in 154 ms, 2,000 x 64 KiB in 273 ms.

## Consequences

- Bend's scalar core is 2.1x behind NEON on one core: it hashes one chunk at
  a time, where NEON hashes four. That gap is the next target (ADR 0002).
- The GPU path is already within 1.3x of rayon's 18 cores, with no tuning.
- The fork tree goes all the way down to single chunks; leaf size and the
  host/device split are untuned.
