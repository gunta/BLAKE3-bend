# ADR 0007: Laws and proofs

Date: 2026-10-26
Status: accepted

## Context

Bend's checker is a prover: a law states a claim, a def of the same name
proves it, and `bend PROOF.bend` prints ALL PROOFS CHECK only when every
law holds (the guide's "Laws and Proofs"). The port had none. Its only
evidence was running the official vectors (`test/vectors.bend`) and the
big-file test against the official `b3sum`.

Two facts set the design:

- **Array.fork is `@unsafe` in Base** (it returns one array twice). Every
  tree used it, so `hash`, `hash1` and the trees "relied on unsafe code",
  and any file importing `blake3.bend` printed SOME PROOFS FAIL, laws or
  not. The checker names the fix: move those defs to a file the proof does
  not import.
- **U32 is `Word(32n)` of Bools** in Base, so the checker evaluates U32
  code exactly, but slowly: an add is 32 full adders, and `x >> 16n` is 16
  one-bit shifts, so a rotation costs ~1.6 ms and a compression ~0.6 s.
  On symbolic inputs it compares terms in lock step, so a law over every
  input proves in seconds when both sides build the same term.

## Decision

- **The trees take the read-sharing as a template**, `~dup`. `blake3.bend`
  (generated) has no `@unsafe` def left; `hash.bend` holds the entry points
  that run (`H.hash`, `H.hash.at`, `H.hash1`, `H.hash1.at`), each the
  blake3.bend tree with `~fork` (Array.fork). The laws pass `~share`
  (Array.clone). A template compiles to its own copy per argument, so the
  emitted C differs only by a one-call `fork` wrapper: same text size, and
  interleaved 1 GiB GPU runs gave 13.77 vs 13.74 ms medians (machine under
  outside load). Callers (`b3io`, `bench/mem`, `bench/file`,
  `test/vectors`) import `hash.bend as H`.
- **`LAWS.bend` states the claims and `PROOF.bend` proves them**, both
  generated by `tools/gen_laws.py` (the vectors' digests, the 64- and
  128-field record patterns, and MSG_SCHEDULE read from
  `c/blake3_impl.h`).

## The laws (all proven)

| law | what it says | proof |
|-----|--------------|-------|
| `kat.hash.len{0,1,64,65,1023,1025,2049,3073,8193}` | the CPU tree (`hash`) gives the official digest | `{==}`: the checker runs BLAKE3 |
| `kat.hash1.len{0,2049}` | the GPU tree (`hash1`) too | `{==}` |
| `kat.g4.len4096` | the GPU flat leaf g4 over 4 chunks, with ROOT, is the 4096-byte digest | `{==}` |
| `kat.segs.len2048` | two one-chunk spans (`hash.at`, counter bases 0 and 1) and a ROOT parent give the 2048-byte digest, as b3sum merges a big file's parts | `{==}` |
| `compress8.lane` | for **every** input, lane l of compress8 is compress of lane l, counter `ctr + step * l` | open the records, `{==}` on symbolic terms (8 cases) |
| `par8.lane` | for every input, lane l of par8 is the parent of the right pair of lanes | same |
| `schedule` | perm applied r times is row r of the C code's MSG_SCHEDULE, for every block | `{==}` |
| `tree1.digits` | blake3.bend's tree1 split rule (n > 2^p) equals `tree(digits(n - 1))` for every input of 1 to 1024 chunks | `{==}` by computation, not induction |
| `segments` | for all k, j, r: the tree over chunks 0..r is the tree over its 2^k-chunk segments, each complete but the last (ADR 0004) | induction, 5 lemmas |
| `levels` | for all k, r: k levels of pairing neighbours (odd one carried up) leave r >> k complete subtrees and the tree of the rest | induction, 3 lemmas |
| `levels.root` | so once 2^k > r, a level-by-level GPU reduction is BLAKE3's tree | `levels` and `Equal.trans` |

The tree laws are about a `Shape` (a tree with the chunks at its leaves),
so they hold for any compression function. BLAKE3's tree over chunks
0..r is `tree(digits(k, r, []))`: read the binary digits of the last
chunk's index from the top; a 1 at a node of depth d splits off the complete
tree over the first 2^(d-1) chunks. With digits the two theorems need no
division or powers: a segment index and an offset are a split of the digit
list (`tree_append`), and a level of pairing moves the low digit of the
count into the last tree (`pairs_row`).

## Results

`bend/prove.sh` (`bend PROOF.bend` with build.sh's deep stack): ALL PROOFS
CHECK, 20 laws, in 224-244 s on the M5 Pro (under outside load), almost all
of it the known-answer laws (~0.6 s per compression; 8193 bytes alone is
~95 s). The lane, schedule and tree laws take ~9 s together, `tree1.digits`
~9 s.

`bend PROOF.bend --verdict` (the Lean-proven kernel) did not run: it needs
Lean v4.34.0 (`elan toolchain install leanprover/lean4:v4.34.0`), and this
machine has v4.35.0.

## What is not proven

- The laws are about the trees with `~share` (Array.clone); the entry points
  that run pass `~fork` (Array.fork). That the two agree rests on
  Array.fork's contract (two handles that read as the input), which Base
  cannot prove: it is `@unsafe`. Nothing else differs between them.
- The known answers pin small inputs. Leaf32 (32+ chunks), g16 and g64
  (64+ MiB on the GPU) are too slow for the checker (~0.6 s a compression)
  and stay covered by the runtime vectors (`test/vectors.bend`, up to
  102400 bytes) and `test/big.py`. g16 and g64 are the generator's same
  template as g4.
- Laws about arrays cannot be universal: a read of a symbolic array is
  stuck, so the loaders (`ld`, `ld8`) are covered only by the known
  answers.
- `tree1.digits` is exhaustive up to 1024 chunks, not an induction; the
  general bridge needs Nat lemmas on halving and powers of two.
- A false law over symbolic inputs can make the checker run for minutes
  instead of failing (lock-step comparison fails, then it normalizes); a
  wrong lane law was still running after 300 s.
